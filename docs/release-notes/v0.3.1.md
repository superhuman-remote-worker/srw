# SRW v0.3.1

v0.3.1 is a patch release: `helm upgrade` with `--version 0.3.1` and your existing values.
It fixes three faults that a fresh installation with an external Nextcloud and databases on
CloudNativePG ran into. Nothing in it needs operator action, and it runs no database
migration.

## Highlights

- **An external Nextcloud works as a main cloud again.** Since 0.0.24, SRW proves which
  installation its main cloud is before any cloud effect, and with `cloud.externalBackend:
  nextcloud` it never could: it read the installation's instance id from `status.php`, which a
  stock Nextcloud does not fill, and the signed lane of the bundled Nextcloud does not exist on
  an external one. Every cloud feature stayed off (project folders, "Open folder", shares,
  deliverable export and session mounts), and only a log line said so. SRW now also reads the
  id from the name of the session cookie that the server's login page sets. An external
  Nextcloud still needs no SRW app, and the bundled Nextcloud is unchanged. See
  [Cloud folders](https://docs.superhuman-remote-worker.com/cloud-folders/#for-operators).
- **When the main cloud is off, you see why.** **Settings → Main cloud** says when SRW has not
  established the cloud's installation, and why: the cloud does not answer, it names no
  installation, or it is not configured. A project created meanwhile says it has no cloud
  folder yet instead of saying nothing; SRW creates the folder when the project is opened after
  the cloud is back.
- **A fresh install on CloudNativePG starts.** With `databases.vector.engine: cnpg`, the
  database owner `srw` is no superuser and cannot create the `vector` extension, so the
  orchestrator stopped at its first migration and the release failed. A new CloudNativePG
  Cluster now creates the extensions SRW's migrations need as the superuser right after
  `initdb`, from the list the StatefulSet engine uses. An existing Cluster is not touched.
- **pgAdmin on CloudNativePG or an external database.** pgAdmin connected to the StatefulSet
  Service names and waited for them before it started, so with any of the three databases on
  CloudNativePG its pod never left `Init` and every `helm --wait` ran into its timeout. It now
  uses the host and port every other component uses, and does not wait.

## Upgrading from 0.3.0

- An installation with an external Nextcloud adopts it at the first start of 0.3.1: the log
  line "main-cloud authority remains unavailable" stops, and **Settings → Main cloud** shows
  an installation id. A project created while the cloud was off gets its folder when it is next
  opened. If a reverse proxy in front of Nextcloud drops `Set-Cookie` headers, SRW still has
  no id; the Main cloud page says so.
- If your fresh CloudNativePG install of 0.3.0 or earlier needed the manual
  `CREATE EXTENSION vector` workaround, nothing changes for it: the extension is there.
- The pgAdmin Deployment's pod template changes (its init container is gone), so its pod is
  recreated once.
