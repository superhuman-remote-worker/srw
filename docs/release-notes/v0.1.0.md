# SRW v0.1.0 — public beta

v0.1.0 is the first public release of SRW. It is a beta: read the
[security model](https://docs.superhuman-remote-worker.com/security-model/) before you connect
valuable systems. From this version on, the version number tells you whether an upgrade needs
your attention.

## What SRW is

A self-hosted runtime for AI work. You combine three building blocks: an expert (prompt, model,
tools), a workspace (none, files in your object store, a throwaway pod, or a VM) and connectors
(repositories, databases, cloud folders, email, MCP servers, knowledge bases). SRW runs them on
your own Kubernetes cluster as a live session or an autonomous job.

## Highlights

- **Install from a generator.** [superhuman-remote-worker.com/configure](https://superhuman-remote-worker.com/configure)
  writes the values, Secrets and an install script for a fresh k3s node or an existing cluster.
- **One model key is enough.** One OpenRouter API key covers all four model roles (chat,
  auxiliary, embedding, rerank), and both the generator and the local example seed them. See
  [Models](https://docs.superhuman-remote-worker.com/models/).
- **Documentation site.** [docs.superhuman-remote-worker.com](https://docs.superhuman-remote-worker.com/)
  has getting started, concepts, guides, troubleshooting and a Helm values reference generated
  from the chart.
- **Release notes and a versioning policy.** Every release now gets notes like these. Before
  1.0, a minor version means an operator must act; a patch is a drop-in `helm upgrade`. See
  [Versioning and upgrades](https://docs.superhuman-remote-worker.com/versioning/).
- **Sessions change workspace in place.** A Session on Virtual or None can move up to a
  Container or a VM, by `/upgrade-workspace` or when the agent asks, and keeps its conversation.
  Its files are copied over; a file too large to copy stays behind and is named.
- **`read_only` replaces `supervised`.** The lowest permission mode now reads files, searches,
  browses and fetches pages without asking. It asks before it writes, acts outside the workspace
  or runs a command. The model is told which mode it is in.
- **Attach and dictate on New chat.** Files and dictation work on the New chat screen before the
  session exists, and go with the first message.
- **The agent's shell has the image's tools.** In a workspace shell, Playwright finds the bundled
  Chromium, and `pip install` and `npm install -g` work for the agent.
- **Every bundled expert can load skills.** `use_skill` is its own tool category, so an expert
  that writes its own tool list keeps it. Eight bundled experts had lost it that way.
- **Local phone lines (optional).** The voice gateway and an Asterisk addon answer calls on your
  own phone system with models you run. Both are off by default. See
  [Local phone lines](https://docs.superhuman-remote-worker.com/voice-gateway/).

## Upgrading from 0.0.x

The chart and image names are unchanged: `helm upgrade` with `--version 0.1.0`. Read this whole
section first. The GitHub Release also lists each commit marked as needing operator action.

- **The API accepts only access tokens issued to SRW's own clients.** A Keycloak Bearer token is
  refused (401) when it is an ID token, or when its `azp` is neither the Cockpit BFF client
  (`auth.bff.clientId`) nor the Cockpit SPA client (`keycloak.cockpitClientId`) and its `aud`
  names no allowed audience. Cockpit sign-in is unaffected. A script or integration that calls
  the API with another client's token needs one of three changes: switch it to a personal access
  token, give its Keycloak client a hardcoded `orchestrator-api` audience mapper, or list the
  client and send its access token (it needs a `sub` claim):

  ```yaml
  auth:
    oidc:
      extraAllowedClients:
        - my-cli            # access tokens with azp: my-cli are accepted
      allowedAudiences:
        - orchestrator-api  # the default; keep it when you set this list
  ```

  Never list a client whose tokens another application holds (Gitea, Nextcloud, OpenCloud,
  `admin-cli`): its holder could then call the API as the user. See
  [Identity and API credentials](https://docs.superhuman-remote-worker.com/security-model/#identity-and-api-credentials).
- **Two chart defaults changed.** In `workspace.networkPolicy.tiers`, `internet-only` now
  denies every private range, and `home-allowed` no longer denies `10.0.50.0/24` and
  `10.0.51.0/24`. Redeclare both tiers in your values with your node and load-balancer ranges
  (Helm replaces a list as a whole). `orchestrator.kbGitAllowedHosts` no longer defaults to
  `git.srw.works,srw-gitea:3000`: with `gitea.enabled`, the release's own Gitea is trusted
  without being listed. List any other Git host a knowledge-base datasource reads, apart from
  github.com, gitlab.com, bitbucket.org and codeberg.org.
- **Stateless Sessions and container startup tracking are on by default**
  (`agent.stateless.enabled`, `orchestrator.containerStartupStageAuthority.enabled`). The chart
  now runs a pool of executor Pods (`agent.stateless.replicas`, 2). Keep pinned agent
  provisioning available too: a Session that moves to a VM moves to a dedicated agent.
  `agent.stateless.enabled: false` keeps every Session pinned. **Upgrading from v0.0.28 or
  older, roll twice:** upgrade with `orchestrator.containerStartupStageAuthority.enabled: false`,
  check that every older orchestrator Pod and process is gone, then upgrade again with it on. See
  [Container startup stage rollout](https://github.com/superhuman-remote-worker/srw/blob/main/helm/README.md#container-startup-stage-rollout).
- **The chart now creates a ClusterRole by default.** With stateless Sessions on,
  `agent.stateless.processZeroFinalizer` (on by default) renders
  `<fullname>-<namespace>-orchestrator-node-observer`: a ClusterRole and ClusterRoleBinding that
  let the orchestrator `get` Nodes by name, with no list or watch. It needs them to release an
  executor whose Node is gone. An installer whose rights end at one namespace can't create them.
  Have a cluster administrator run that install, or read the comment on
  `agent.stateless.processZeroFinalizer` in `values.yaml` and set it to `false`.
- **New Sessions start in `read_only`.** It is `supervised` renamed (migrations 0554 and 0555),
  and it now runs reads without asking. Sessions stored as `supervised` behave as `read_only`,
  and the API still accepts the old name. `auto_accept` now also asks before external actions:
  deletes, mail, pushes, datasource writes, job control, delegation, and MCP tools that declare
  no effect.
- **A model id names one catalog row** (migrations 0552 and 0553). If two providers held the same
  id, 0552 keeps the bare id on the row SRW already routed to and renames each other row to
  `<id>-<provider>`. A renamed row keeps sending the old name upstream as its served model id, and
  keeps its UUID. Routing does not change. 0553 then makes the id unique; it builds the index
  concurrently, so writes stay available. From now on, Settings → Administration → Models
  refuses (409) an id another provider holds and suggests a free one. An `llm.seed` entry whose
  id another provider holds is skipped, with a log line saying why: give it its own `id` and set
  `servedModelId`.
- **A 3072-dimension embedding model never works.** If Settings → Administration → Models lists
  `openrouter/openai/text-embedding-3-large` (which `python init.py` added for an
  OpenRouter-only key), disable it and use Qwen3 Embedding 8B. SRW stores 4096-dimension vectors.
- **Custom workspace images:** the agent's SSH sessions don't inherit Dockerfile `ENV`. After
  your `ENV` lines, add `RUN /usr/local/bin/write-agent-environment NAME ...` with the names you
  set. The base images no longer set `PIP_TARGET`, so pip run as root installs system-wide
  without unsetting it. See
  [Workspace images](https://docs.superhuman-remote-worker.com/workspace-images/).
- **Idle job Pods:** with `orchestrator.workspaceCleanupReconciliationEnabled: true`, a job left
  paused, in review or waiting for a reply now releases its workspace Pod after 24 hours and keeps
  its volume; the next resume recreates the Pod. `workspace.idlePodReleaseSeconds: 0` turns this
  off. Installs with the flag off (the default) are unchanged.
- Pin `~0.1.0` to receive drop-in patches only.

## Security fixes

Fixed since v0.0.30:

- Cross-site scripting on the MCP server's OAuth consent page.
- Cross-site scripting in Session chat code blocks.
- A cited HTML or SVG snapshot no longer renders on the Cockpit origin, and the API serves
  snapshots as downloads.
- A citation's web fetch takes http and https only, and refuses private, loopback, link-local
  and metadata addresses at the first URL and at every redirect.
- A profile can be edited only by its user or an administrator, and the e-mail address can no
  longer be changed through the API.
- Deregistering an agent through MCP needs an administrator.
- A read-only database connector stays read-only: `sql_query` runs one statement, and
  `mongo_aggregate` refuses `$out` and `$merge`.

## Known limitations

- Beta: run it single-tenant, for users you trust, and start with disposable data.
- Embedding models must produce 4096-dimensional vectors. Readiness does not check the size yet,
  so a wrong model shows up only as errors in the orchestrator log.
- Agent pods have no egress NetworkPolicy by default (`agent.networkPolicy.enabled: false`);
  workspaces do.
- **Container workspaces run privileged by default.** SRW's own workspace images run privileged,
  with seccomp `Unconfined`, so rclone can mount cloud folders with FUSE. A Session whose cloud
  folders come from the in-pod plane's sidecars runs unprivileged. To run no privileged
  container, set `workspace.fuse.enabled: false` and `cloud.rcloneMount.allowContainer: false`;
  a Container Session then gets its outbox but no mounted cloud folders.
- **Cloud credentials in the workspace.** OpenCloud folders put an access token of the
  orchestrator's service account into the workspace, and a Nextcloud folder mounted inside the
  workspace puts its login there. Content the agent processes can try to get code run that reads
  them. See
  [Cloud folders and their credentials](https://docs.superhuman-remote-worker.com/security-model/#cloud-folders-and-their-credentials).

## Known issues

- **Bundled Postgres can fail initdb on ext4 volumes.** The bundled database StatefulSets use the
  volume's root as the data directory. An ext4-formatted volume (Longhorn, most cloud block
  storage) has `lost+found` there, so initdb refuses the directory and the Pod restarts. Give the
  databases a `local-path`-style StorageClass (`databases.<name>.storageClass`), or run them on
  CloudNativePG (`databases.<name>.engine: cnpg`, with the operator installed first; see
  [Bundled databases on CloudNativePG](https://github.com/superhuman-remote-worker/srw/blob/main/helm/README.md#bundled-databases-on-cloudnativepg)).
